# Kubernetes deployment for data-philter

This folder contains Kubernetes manifests and a Kustomize configuration to deploy data-philter and the druid-mcp-server into a cluster.

## What gets created

- Namespace: `data-philter`
- Deployment + Service: `druid-mcp-server` (ClusterIP)
- Deployment + Service: `data-philter` (NodePort `30400`)
- PersistentVolumeClaim: `data-philter-data` (1Gi) mounted at `/data`
- ConfigMaps generated via Kustomize for application settings

## Prerequisites

- A working Kubernetes cluster and `kubectl` configured to point to it
- `kustomize` CLI (kubectl also supports `-k` natively)

## Quick start (recommended: Kustomize apply)

Apply all resources using Kustomize:

```bash
kubectl apply -k k8s/
```

Verify:

```bash
kubectl get ns data-philter
kubectl get all -n data-philter
```

Access the app:

- The `data-philter` Service is exposed as NodePort `30400`. If your cluster nodes are reachable, open:
  - http://<node-ip>:30400
- Alternatively, port-forward locally:

```bash
kubectl -n data-philter port-forward svc/data-philter 4000:4000
# Then open http://localhost:4000
```

## Render with Kustomize first (optional)

If you prefer to generate a single manifest file and review/commit it:

```bash
# Using kubectl (v1.14+ has builtin kustomize)
kubectl kustomize k8s/ > dist.yaml

# Or using the kustomize binary
kustomize build k8s/ > dist.yaml

# Apply the rendered manifest
kubectl apply -f dist.yaml

# Delete later with
kubectl delete -f dist.yaml
```

## Applying plain manifests without Kustomize

You can apply the base deployment file directly, but note that ConfigMaps are normally generated by Kustomize:

```bash
kubectl apply -f k8s/
```

If you skip Kustomize, you must also create the ConfigMaps that Kustomize would generate (`druid-env` and `data-philter-app-env`).

## Configuration

- Environment variables are defined in `k8s/kustomization.yaml` using `configMapGenerator.literals`.
  - Edit that file to set values that match your environment (e.g., `DRUID_ROUTER_URL`, `IUNERA_MODEL_TYPE`, API keys, etc.).
- Namespace
  - The manifests and kustomization default to the `data-philter` namespace. Change the `namespace` field in `k8s/kustomization.yaml` if needed.
- Storage
  - The default PersistentVolumeClaim requests `1Gi` and uses `ReadWriteOnce`. Ensure your cluster has a default StorageClass. Adjust `k8s/deployment.yaml` if you need different storage settings.
- Images
  - The deployments use the images:
    - `iunera/druid-mcp-server:latest`
    - `iunera/data-philter:latest`
  - You can pin versions by editing `k8s/deployment.yaml` or by using a Kustomize `images` transform in `k8s/kustomization.yaml`.

## Common operations

Check rollout status:

```bash
kubectl -n data-philter rollout status deploy/data-philter
kubectl -n data-philter rollout status deploy/druid-mcp-server
```

View logs:

```bash
kubectl -n data-philter logs deploy/data-philter -f
kubectl -n data-philter logs deploy/druid-mcp-server -f
```

## Uninstall

If you applied using Kustomize directly:

```bash
kubectl delete -k k8s/
```

If you applied a rendered file:

```bash
kubectl delete -f dist.yaml
```

## Notes

- Security & credentials: Do not commit secrets into `kustomization.yaml`. For production, consider using Secret resources (generated from sops, sealed-secrets, external secret stores, etc.).
- NodePort exposure: For production, prefer an Ingress or LoadBalancer Service type instead of NodePort. You can patch Service type via Kustomize overlays if desired.
